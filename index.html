System Incident Report

ROOT CAUSE The "Thundering Herd"

During the flash sale, 10,000 users attempted to buy the exact same item simultaneously.

To prevent data corruption, PostgreSQL applies an ExclusiveLock to that specific inventory row. Only one user can update the row at a time.

The other 9,999 users were placed in a queue. Because they could not finish their queries, they held their database connections open, exhausting the Web Server connection pool. Any new user—even someone buying a different item—received a 500 Gateway Timeout.

REMEDIATION How SREs Fix This

  • Tier 1: Fail Fast (Database config)
    Set lock_timeout = '2s'. Abort queued queries quickly to free up connections rather than crashing the site.
  • Tier 2: The Traffic Cop
    Deploy PgBouncer. If K8s web servers autoscale, PgBouncer queues connections safely in memory to protect the Postgres VM.
  • Tier 3: Architectural Decoupling
    Stop writing directly to SQL. Send checkout intents to an asynchronous queue (Kafka or Redis) and process the database updates in the background.
